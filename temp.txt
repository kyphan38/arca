[Fundamental]: What are the three main states a process can be in?	Running (currently executing on CPU with context in CPU registers), Blocked (cannot run, waiting for an event like I/O completion), and Ready (able to run but waiting for the OS scheduler to assign it a CPU core). The context of blocked and ready processes is saved in OS memory.
[Fundamental]: What information does a Process Control Block (PCB) contain?	A PCB stores the process's PID, current state (running, ready, blocked, terminated), pointers to related processes (parent, children), saved CPU context for when the process is not running, information about the process's memory locations, and information about ongoing I/O communication. In Linux, this structure is called task_struct.
[Fundamental]: What four components define a process beyond just "a running program"?	A unique Process Identifier (PID), a memory image in RAM (code, data, stack, heap), an execution context (CPU register values including the Program Counter), and I/O state (open files, network connections, and other I/O information).
[Fundamental]: What is BIOS and what role does it play during boot?	BIOS (Basic Input Output System) is firmware stored in non-volatile memory on the motherboard. It is the first code that executes when a computer powers on. Its job is to initialize hardware components and then locate and hand off control to a boot loader on the boot disk.
[Fundamental]: What is the CPU scheduler's basic operation?	The OS maintains a list of all PCBs. The scheduler loops through this list, picks a ready process to run on each available CPU core, and periodically performs context switches between processes to share the CPU.
[Fundamental]: Why does the OS move a process to blocked state when it requests I/O instead of letting it wait on the CPU?	If the process stayed on the CPU while waiting for a slow I/O device, the CPU would sit idle wasting cycles. By moving the requesting process to blocked state, the OS frees the CPU to run another ready process. The blocked process will be moved back to ready only when the I/O device signals completion via an interrupt, ensuring no CPU time is wasted on waiting.
[Fundamental]: Why does a process's execution context reside in CPU registers while running but must be saved to memory when paused?	CPU registers are the only place the processor can directly use state like the Program Counter and data registers during execution - but there is only one set of registers per core. When the OS pauses a process to run another, it must copy those register values into the PCB in memory, because the incoming process needs those same physical registers for its own state. Without saving to memory, the paused process's progress would be permanently lost.
[Fundamental]: How does a process transition from blocked back to running?	A blocked process cannot go directly to running. When the event it is waiting for completes (e.g., a disk signals data readiness via an interrupt), the OS interrupt handler moves the process from blocked to ready state. The process then waits in the ready queue until the scheduler selects it for execution, at which point the OS restores its saved context to the CPU registers and it enters the running state.
[Fundamental]: Why does modern OS booting require a two-step bootloader process instead of loading the OS directly from BIOS?	BIOS is designed to load code from the first 512-byte sector of the boot disk - this constraint exists so BIOS can find the bootloader at a fixed, predictable location. However, modern OS kernels are far too large and complex to be loaded by a 512-byte program. So the first-stage bootloader fits in 512 bytes and its only job is to load a second, larger bootloader that has the full capability to read large kernel images from disk or network and set up the environment before transferring control to the OS.
[Fundamental]: Why does the PCB store pointers to parent and child processes?	Processes in an OS form a hierarchy - every process (except the initial one) is created by a parent process. The OS needs these relationships for lifecycle management: when a parent terminates, the OS must decide what happens to its children, and a parent may need to wait for a child to finish or collect its exit status. Without these pointers, the OS could not traverse or manage the process tree.
[Fundamental]: Why is the PCB stored in kernel memory rather than in the process's own address space?	The PCB contains sensitive control information - process state, CPU context, memory mappings, I/O state - that the OS needs to manage scheduling and isolation. If it were in user-space memory, a buggy or malicious program could modify its own PCB to escalate privileges, change its state, or corrupt scheduling data. Keeping it in kernel memory means only the OS in Kernel Mode can read or modify it, preserving system integrity.
[Fundamental]: How does the OS initialize a new process when a program is launched?	The OS creates a new process by assigning it a unique PID, building a PCB to track its information, and allocating a memory image in RAM that includes the code and data loaded from the executable plus a stack and heap for runtime use. It then initializes the CPU context - setting the Program Counter to the program's entry point and other registers - and starts the process in user mode. The process is placed in the ready queue for the scheduler.
[Fundamental]: Walk through the P0 and P1 state transition example from the notes, explaining why each transition occurs.	Initially P0 is running and P1 is ready. P0 requests disk data via a system call - since the data is not immediately available, the OS cannot let P0 spin on the CPU waiting, so it moves P0 to blocked state. The OS then context-switches to P1, which enters running state. While P1 runs, the disk finishes and sends an interrupt. The CPU jumps to the OS interrupt handler, which moves P0 from blocked to ready (not directly to running, because P1 is still executing). The scheduler may continue running P1 and switch to P0 later, demonstrating that ready does not mean immediately scheduled.
[Fundamental]: Walk through the complete boot sequence from power-on to a user being able to launch programs.	When the system powers on, the CPU begins executing BIOS code stored in non-volatile memory. BIOS initializes hardware components, then scans for a boot disk and loads the first-stage bootloader from its 512-byte first sector. This simple bootloader's job is to locate and load a more capable second-stage bootloader. The second-stage bootloader sets up CPU registers, reads the large OS kernel image from disk into memory, and transfers control to the kernel. The OS kernel then executes its initialization routines and eventually exposes a user terminal or interface, at which point the user can start launching programs that the OS will manage as processes.
[Fundamental]: Walk through what happens to a process's context during a full context switch from Process A to Process B.	Process A is running, so its execution context (PC, registers) lives in the CPU's physical registers. The OS decides to switch - it copies all of A's register values from the CPU into A's PCB in kernel memory and sets A's state to ready or blocked. The OS then looks up B's PCB, reads B's previously saved register values, and loads them into the CPU's physical registers - including B's Program Counter, which points to whatever instruction B was about to execute when it was last paused. The CPU resumes fetching instructions from B's PC, and B is now running as if it had never stopped.
[Interview]: During an incident, you notice a server running hundreds of processes but only a handful of CPU cores. A teammate asks how the system handles this without crashing. Explain the mechanism and what you would monitor.	Key points to cover: • OS uses CPU scheduling - maintains PCBs for all processes, scheduler picks ready processes to run on available cores • Context switching rapidly swaps processes on/off each core, creating the illusion of concurrency • Monitor: number of runnable processes vs cores (load average), context switch rate (vmstat cs column), run queue length • High load average relative to core count means processes spend more time in ready state waiting - increased latency • Trade-off: more processes = more context switch overhead = less actual useful work per core • Tools: uptime, top, vmstat, /proc/loadavg, pidstat -w for per-process context switch counts
[Interview]: Your monitoring shows a critical service process has been in a blocked state for an unusually long time. Walk through how you would diagnose what it is waiting for and decide on a course of action.	Key points to cover: • Blocked means waiting for an event - typically I/O completion (disk, network), a lock, or a signal • First identify what it's blocked on: cat /proc/[pid]/wchan shows the kernel function, strace -p [pid] shows the system call it's stuck in • If blocked on disk I/O: check iostat, iotop, dmesg for disk errors - could be a failing drive or NFS timeout • If blocked on network: check ss, netstat for stuck connections, lsof for open file descriptors/sockets • If blocked on a lock: check /proc/[pid]/status, consider using perf or gdb to identify the contending process • Decision framework: if the I/O source is recoverable (restart NFS, fix disk), do that; if not, consider whether killing the process is safe (check if it's in D state - uninterruptible sleep cannot be killed) • Mention the state transition model: blocked → ready only happens when the awaited event completes - no shortcut
[Interview]: A junior colleague wants to understand why the boot process is so complex - they ask why the OS kernel can't just start running when you power on the machine. How would you explain it?	Key points to cover: • CPU needs firmware (BIOS) at a known memory address to start executing - the OS kernel is too large and complex to be at a fixed hardware location • BIOS is simple: initialize hardware, find the boot disk, load the first 512 bytes - this constraint is a hardware/firmware design limitation • Boot is a chain of trust: BIOS → first-stage bootloader (512 bytes, simple) → second-stage bootloader (complex, can read filesystems) → OS kernel • Each stage is just capable enough to load the next more capable stage • Practical relevance: understanding this matters for troubleshooting boot failures (GRUB rescue, missing bootloader), configuring PXE/network boot in data centers, and understanding UEFI Secure Boot chains • Mention: modern UEFI replaces legacy BIOS but still follows a staged approach
